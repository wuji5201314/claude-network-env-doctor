# 误报清单与概念纠错

## 不要为这些改配置

| 看起来像问题 | 实际情况 |
|---|---|
| DNS 泄漏测试里出现不同地区或网络的解析器 | 解析器位置可以与代理出口位置不同，也可能是分流或检测页缓存。先核对解析器运营商、当前客户端路径和用户预期；地理位置不一致本身不是泄漏证据 |
| DNS 出口显示 Google/Cloudflare，IP 与网页出口不同或定位到别的地区 | 这是递归 DNS 解析器的地址，不是网页 TCP 出口。公共 DNS 可能从不同地区的递归节点响应；解析器 IP 或城市与代理出口不一致，不足以判定泄漏 |
| 显示"Found 96 Servers, 5 ISP, 4 Locations" | 回答解析请求的服务器数量，不是泄漏条数 |
| 出口 IP 是 `Corporate / Hosting`、风险分偏高 | 节点是机房 IP，本机无关，换节点才能变 |
| TCP/IP 指纹显示 `OS = Android` | UA 或扩展导致的误判 |
| 第三方站显示的出口国家与所选节点不同 | 节点上游出口，或另一个代理工具在抢流量 |
| `nslookup` 返回 `198.18.x.x` | 仅说明这个系统查询得到了 fake-ip；不排除浏览器 DoH、其他域名或 DNS 上游绕行 |
| `ping` 某 IP 不通 | 节点常丢弃 ICMP，不代表 TCP 不通 |
| 只是 `curl` 超时一次 | 节点抖动；重试并对比另一个节点 |
| 浏览器显示 `IPv6: n/a` | 正常且是好结果，说明没有 IPv6 绕过 |
| 规则模式下部分国外域名走 DIRECT | 规则命中问题，不是"代理坏了"；按域名检查规则 |

## 真问题只有这几类

1. 浏览器 DoH 没关（开关仍是绿色）。
2. 活动网卡启用 IPv6，形成绕过通道。
3. 同时运行两个接管型代理工具（Clash + WARP / FlClash）。
4. 系统代理 + TUN + `HTTP(S)_PROXY` 三者叠加。
5. 浏览器后台进程缓存旧 DNS / 旧连接。
6. TUN 未开导致 DNS 没被接管（仅在要求解析也不外泄时）。
7. 应用不认当前代理方式（Go/Java 只认环境变量等）。

## 为什么 DNS 测试会混排

测试页会解析几十个随机子域名：

- 命中代理规则的 → 由节点侧 DNS 解析 → 显示国外解析器；
- 未命中、走 DIRECT 的 → 由本地 DNS 解析 → 显示用户当前网络所用的解析器。

所以不同解析器可能来自分流。若要求所有查询都不经本地 ISP，检测中出现 ISP 解析器是需要追查的信号，但应先确认它确实是 ISP 递归解析器，而非仅按 IP 地理库判定；然后在同一浏览器、同一代理状态下复测，并对照本机 DNS 上游或代理连接记录。若使用分流，应核对测试域名命中的规则。检测页通常使用随机子域名，一次检测不能证明 Claude 的每个域名都走了相同 DNS 路径。

DNS 泄漏判断看查询是否越过用户预期的解析路径，不要求 DNS 递归解析器 IP 与网页出口 IP 相同。公共 DNS 的 Anycast/调度可能让查询落到不同地区的服务节点；“Google（香港）+ 网页出口（美国）”可以与代理正常工作同时成立。反过来，检测页标记“未检测到泄漏”也只代表它本次测试没有观察到异常，不是所有应用、域名和时段都已证明安全。

## 概念纠错

| 错误说法 | 正确理解 |
|---|---|
| "TCP 请求访问的是域名解析的 DNS" | TCP 连接的是 IP；DNS 只负责把域名翻译成 IP |
| "DNS 泄漏 = DNS IP 和网页出口 IP 不同" | DNS 泄漏看**目标域名的解析请求是否意外绕过预期解析路径**；递归解析器地址与网页出口地址通常本来就不同 |
| "nslookup 返回 198.18 是假 IP，所以有问题" | 这是 fake-ip；它只说明本次系统查询拿到了代理使用的合成地址，不代表浏览器 DoH 或其他查询也走同一路径 |
| "选了 Cloudflare 就关闭/保障了 DoH" | DoH 是解析传输方式；选择提供商不等于关闭 DoH，也不自动保证它走代理。需按预期检查浏览器 DoH 与代理路径 |
| "ipconfig 没有公网 IPv6 就永远没有" | 临时地址会消失，用 `curl -6` 或检测站复核 |
| "检测站说泄漏就一定要改" | 先对照本清单，再决定是否动手 |
| "出口国家不对就是本机配错了" | 出口由节点服务器决定，本机只能换节点 |
| "开了 Windows 系统代理，curl.exe 就会自动走代理" | Windows 自带 `curl.exe` 不读系统代理（WinINET），只读 `HTTPS_PROXY`/`ALL_PROXY` 环境变量、`-x` 参数或 TUN |

## 判定优先级

出现矛盾结果时，按这个顺序取信：

1. `curl https://ip.sb` 的出口 IP（TCP 层事实）
2. `nslookup 目标域名`（DNS 归属）
3. 代理工具「连接」页里该域名的链路（规则命中）
4. 浏览器检测站的 IP / IPv6 / WebRTC（浏览器层）
5. 第三方风险评分、指纹信息（参考，不作为修复依据）
